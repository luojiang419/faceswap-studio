# 原生维护验收超时与事务恢复

2026-10-20，工作台拖拽功能正式发行时验证。

## 表现与根因

本机 `--repair-root` 没有输出最终报告，外层 Python 验证脚本在 210 秒后抛出 `TimeoutExpired`。检查发现新应用文件已经写入，安装登记仍为旧发布序号，原生维护停在替换后的完整复检阶段。

维护包含完整运行文件检查、必要的包下载、逐文件替换及完整复检；固定的短时限不能覆盖所有机器与网络。`subprocess.run(timeout=...)` 到期会杀死子进程，报告缺失不代表没有修改文件，也不代表原生维护已主动回滚。

## 处理

- 发行验收应预留足够时间，本次本机辅助脚本改为 600 秒；不要用短时限直接终止正在操作安装目录的维护进程。
- 复用已经校验的本地应用 ZIP。原生维护支持从安装器同目录取得匹配大小、SHA-256 的应用包，同卷可建立只读用途硬链接，避免重复下载；不修改已发布不可变资源。
- 中断后先确认所属工作台与维护进程已退出，保留 `%LOCALAPPDATA%/FaceSwapStudioMaintenance/sessions/<会话>` 中的 journal、backup、stage 和诊断。只操作能确认属于本次安装的会话。
- 必须回到原状态时，先逐项校验 journal 的安装根、相对路径、外部备份及原存在标识，再按逆序恢复。原先不存在的文件只有在确认为本次新增应用资产、哈希匹配时才可移除。原生卸载入口属于维护文件，应按维护事务规则处理，不能用放宽全部应用更新白名单代替路径检查。
- 恢复后核对备份字节、原发布序号和个人配置哈希；重新运行正式安装器，等待完整成功报告，再复验启动和安装登记。不要只改版本号或把部分替换判为成功。
