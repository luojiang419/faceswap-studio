# Windows 桌面首帧与服务生命周期分离

## 表现与根因

2026-10-20 使用正式 EXE 实测旧安装版首帧耗时 36.649 秒。窗口创建前串行等待 5 秒窗口查找、完整核心导入预检、进程扫描和 Bridge 就绪；窗口关闭后仍持有同一把锁清理服务，期间再次点击会被忽略。

Bridge 的 `/health` 调用 `runtime.status()`，间接持有核心锁、探测 WebUI 并扫描全机 TCP 连接。直接缩短客户端超时会把仍正常启动的服务误判失败，不能只改超时数字。

## 解决方法

- 首先创建真实 Flutter 前端；服务准备放到专用线程，普通无窗口启动不轮询查找窗口。
- 前端锁只约束界面生命周期；另一把 Windows 命名互斥锁覆盖后台服务的启动和清理，并在获得锁的同一线程释放。新窗口可立即显示，后台线程等待旧服务交接。
- 残留清理仅识别本安装的服务，保护新前端与 wrapper；无法找到现存窗口的重复启动等待前端锁，不直接吞掉请求。
- 普通启动直接加载真实服务；完整独立预检留在构建、安装及更新验收。关闭时取消预检和 Bridge 导入并回收进程树。
- Bridge 存活接口直接返回快照，不触碰核心锁或全机网络扫描。核心就绪由专门状态接口和绑定进程、目录、token 的持续健康心跳确认。
- 前端不等待 Bridge 首帧，但必须重试恢复设置、关闭偏好和首帧握手；连接失败展示真实初始化阶段。
- 已可用的内置 FFmpeg 不探测其他系统安装；显式来源覆盖与损坏修复继续保留。

## 验证

`scripts/benchmark_startup.py` 从正式 EXE 计时，以 Flutter 首帧回调显示的真实窗口为终点，检查消息响应；前端关闭后立即重开，不等待旧 wrapper 清理。测试结束确认 wrapper 返回 0、没有服务残留。

开发目录 Release 连续五次首帧 0.578–0.676 秒；本机安装目录连续五次 0.546–1.202 秒。完整推理核心依赖仍在后台加载，不能把界面首帧耗时称为全部模型就绪时间。

配套回归包含真实 Windows 命名互斥锁交接、预检/Bridge 取消、核心锁持有期间的快速健康响应、晚连接与握手恢复，以及真实关闭弹窗和托盘恢复。

Windows UI 测试应枚举并匹配当前测试 PID，不能只匹配 `FLUTTER_RUNNER_WIN32_WINDOW`；RustDesk 等其他程序也会使用此类名。

## 兼容更新后的启动入口必须同步

兼容旧客户端白名单时，应用 ZIP 使用 `启动FaceSwap Studio.exe`，而当前桌面快捷方式指向 `易容 Studio.exe`。若入口整理只在新名字不存在时复制，已有 canonical EXE 将保持旧字节；即使源代码未变，每次 C# 编译的二进制也可能不同，导致最新安装器判坏，后续启动器修改也不会生效。

已验证做法：核对更新清单中的旧入口 SHA-256，确认 canonical 文件属于当前安装；内容不一致时先保留 `integration-backup/易容 Studio.exe`，复制为临时文件后使用 `File.Replace` 原子替换。Windows 已加载的 EXE 可以通过这种方式替换，不能原地覆写。相同内容不重写，同名外部文件和篡改的旧入口拒绝接管。

原生迁移回归 10 项通过；从真实上个发行升级后，入口整理报告 `canonicalEntryUpdated=true`，维护检查 healthy，连续启动 0.556–0.602 秒。
