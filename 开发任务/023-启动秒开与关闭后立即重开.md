## 目标与验收

- 从正式 EXE 启动到真实 Flutter 首帧可见达到秒级；核心、模型和网络检查不得阻塞界面。
- 完全关闭后立即重开、托盘恢复、重复点击均有明确结果，不吞掉重开请求。
- 旧服务清理与新服务启动串行，旧会话不得误杀新前端或新服务；启动中关闭不留下服务。
- Bridge 晚就绪后自动恢复设置、关闭偏好和安装/更新首帧握手；保留独占更新及严格健康检查。
- 记录普通启动、连续重开、服务就绪和清理耗时；区分界面秒开与推理核心就绪时间。
- 仅修改并提交本任务文件，保护既有窗口尺寸、安装脚本、个人配置等改动；不擅自发布公网版本。

## 定位证据

- `notify_running_instance()` 在普通无窗口启动也轮询 5 秒。
- `main()` 串行执行完整独立核心预检、全机进程扫描、Bridge 就绪和模型状态，之后才创建 Flutter 进程。
- 前端退出后，主互斥锁仍覆盖网络停止与进程清理；此时重复启动在找不到窗口后直接退出。
- 前端设置及首帧握手只尝试一次，提前显示界面需要补齐晚连接恢复。

## 实现和中间验证

- 前端立即启动；后台线程独占另一把服务锁，覆盖服务启动和退出清理。前端锁在窗口退出后释放，新窗口可先显示，再等旧服务清理完毕。
- 重复启动找不到窗口时等待接手前端锁；清理只处理本安装的 Python 服务，不再把新前端或上一会话 wrapper 当成残留。
- 普通启动不重复导入整个推理核心进行预检；构建、更新、安装的完整独立预检保留。启动中的 Bridge 和预检可取消并回收子进程。
- Flutter 先恢复本地设置，晚连接后重试远端设置、关闭偏好及首帧握手；界面展示后台初始化阶段和真实错误。
- `GET /health` 独立于核心锁、HTTP 探测及全机 TCP 扫描；未监听的核心端口使用短探测，已可用的内置 FFmpeg 不再探测外部安装。
- 开发版实测：旧安装入口首帧 36.649 秒；启动器第一轮 0.527–0.767 秒；最终 Release 连续五次 0.601 / 0.597 / 0.676 / 0.587 / 0.578 秒，均可响应且零残留。
- 完整启动：首帧 0.662 秒、Bridge 2.750 秒、核心 13.505 秒；晚连接后的 `/updates/healthy` 实际 HTTP 200。
- 首次完整核心验证因原健康接口耗时超过缩短后的超时失败，已修复健康接口耦合后复验通过，未将失败计为成功。
- 原 Windows 集成测试使用通用 Flutter 类名寻找首个窗口，误选 RustDesk；PID 断言阻止了操作。改为枚举并严格匹配当前测试 PID，复验通过，未操作其他应用。
